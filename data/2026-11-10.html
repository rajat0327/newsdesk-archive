Postgres

Nikolay Samokhvalov: UUIDv4 vs UUIDv7: what a random primary key costs in Postgres

This post benchmarks UUIDv4, UUIDv7, and ordered primary keys on Postgres 18 using a 100M row dataset. It quantifies the performance penalty of random keys, showing UUIDv4 inserts at roughly 65% the rate of ordered keys while generating up to 1.9x the WAL volume per row.

Why it matters — Random primary keys like UUIDv4 create significant write amplification and cache churn; switching to time-ordered UUIDv7 can recover ~35% of insert throughput and nearly halve WAL generation.

Performance

Chris van Eijk: json vs jsonb in PostgreSQL: size and speed, measured

A detailed comparison of json and jsonb storage in Postgres 17 and 18 across six different document structures. The results show that while jsonb is often faster to query, it can be up to 41% larger than raw json depending on the document shape.

Why it matters — The common assumption that jsonb is always more efficient is false; document shape dictates whether you gain a 23% size reduction or suffer a 41% storage penalty.

Reliability

Fencing a Postgres primary that might still be alive

This technical deep dive explains the 'fencing' problem in database failover, where a promoted standby must ensure the old primary cannot accept writes. It details specific implementation strategies for bare metal, AWS, and GCP, and explains the rationale behind a fail-open design.

Why it matters — Promoting a standby without a robust fencing mechanism for the old primary risks split-brain scenarios and data corruption during network partitions.

Storage Internals

Lakebase Postgres is built on object storage, but 99.99999% of reads never touch it

The post examines the architecture of running Postgres on top of object storage like S3. It explains how a multi-tiered caching strategy allows 99.99999% of reads to be served from local memory or NVMe, bypassing the high latency of the object store.

Why it matters — Architectural caching can make high-latency, low-cost object storage viable for primary database workloads without sacrificing millisecond-level read performance.

The hidden latency inside your database

An analysis of the 'hidden' network latency that exists inside cloud-managed database clusters, specifically between the compute engine and network-attached storage (NAS). It argues that this internal hop is often a larger bottleneck than the distance between the application and the database.

Why it matters — Optimizing application-to-database latency is futile if the database itself is bottlenecked by the millisecond-scale network hop to its own storage volumes.
