Performance

Alexander Ioffe: I ran the same query twice and Postgres disagreed with itself

The author investigates why two identical EXPLAIN ANALYZE runs on statistically identical data produced opposite query plans (73 vs 3,449 heap blocks) with a tiny 1.5% margin. The post uses ExoBench to measure the planner's behavior and demonstrates an index shape that eliminates this unpredictability.

Why it matters — A tiny statistical margin can cause the Postgres query planner to fluctuate wildly between plans, but specific index shapes can eliminate this unpredictability.

Postgres

Hollis Varden: UUIDv4 or UUIDv7 for a primary key? 5 million rows on PostgreSQL 18

This post benchmarks UUIDv4 against the newly native UUIDv7 primary keys in PostgreSQL 18 using a 5-million-row dataset. The results show that UUIDv7 inserts took 27 seconds compared to 46 seconds for UUIDv4, with the UUIDv4 index being 29% larger, while random lookups performed identically.

Why it matters — Sequential UUIDv7 primary keys can reduce insert times by over 40% and index size by nearly 30% compared to random UUIDv4, without sacrificing lookup performance.

Performance

Chris van Eijk: Row-level security performance in PostgreSQL, measured

Evaluates the performance overhead of Row-Level Security (RLS) policies in PostgreSQL 17. It analyzes the specific costs associated with function volatility, the use of `(SELECT ...)` wrappers, membership subqueries, and how the leakproof rule can inadvertently disable indexes.

Why it matters — RLS policies can silently disable index scans if the underlying functions are not marked leakproof, severely degrading query performance.

How LinkedIn extended ClickHouse from distributed tracing to metric discovery and analytics

Details how LinkedIn scaled its ClickHouse-based observability stack to consolidate over 13 billion metrics into a single index. The system successfully handles more than 150,000 queries per minute, expanding ClickHouse's role from tracing to high-throughput metric discovery.

Why it matters — Consolidating massive-scale tracing and metric data into a unified ClickHouse index can support extremely high query volumes (150k+ QPM) while simplifying observability architecture.
